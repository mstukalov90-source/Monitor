# Что нужно поменять на бэке: построение маршрутов с полевого устройства

**Контекст.** Android-приложение FieldControl получает кнопку «Построение маршрута» в открытом заказе
мониторинга (площадной заказ, `crm.tasks_area`). Маршрут строит существующий движок WebCRM
(`backend/app/crm/order_route.py`, контракт — `order_route_engine.md`); приложение только вызывает API
и рисует результат. До правок ниже API для полевой роли закрыт (`403`), а точку финиша движок не принимает.

Прод-сервер: `http://172.21.198.219` (LAN). Внешний `monitor-crm.mggt.ru` этот функционал не отдаёт и правок не требует.

---

## 1. Роли: пустить `field` в API маршрутов

Сейчас все 4 эндпоинта висят под `require_manager_or_admin` — полевая роль получает 403
(см. `backend/app/routes/order_routes.py`).

Нужно разрешить роль `field` (плюс сервисную роль из п. 3) на:

| Метод | Путь |
|-------|------|
| `POST` | `/api/crm/tasks-area/{key}/build-route` |
| `GET`  | `/api/crm/tasks-area/{key}/route` |
| `GET`  | `/api/crm/tasks-area/{key}/route.gpx` |
| `GET`  | `/api/crm/tasks-area/{key}/route.geojson` |

Вариант реализации: сменить декоратор на собственный `require_route_access`, который пускает
`manager`, `admin`, `field`, `field_service`. Опциональная защита — сверять район заказа
(`crm.tasks_area.rayon`) с `work_zones` пользователя (для сервисной учётки из п. 3 проверку района пропустить).

`built_by` в `crm.order_routes` — логин, от имени которого пришёл запрос (для сервисной учётки это будет
`field_route_service`; при желании можно добавить колонку `built_on_behalf` с логином полевика,
передавать его заголовком `X-Field-User`, — необязательно).

## 2. Точка финиша в build-route

Сейчас `POST build-route` принимает только `start_lng` / `start_lat`. Приложение даёт полевику выбрать:

- **точку старта — обязательно**;
- **точку окончания — опционально**.

Нужно добавить в тело запроса опциональные:

```json
{
  "start_lng": 37.4177,
  "start_lat": 55.8745,
  "end_lng": 37.4301,
  "end_lat": 55.8702
}
```

Логика движка:

1. Если задан `end_*` — снапнуть точку финиша к графу (как старт, тот же порог 500 м; не снапнулась → 400).
2. Точка финиша добавляется **последним** waypoint'ом.
3. Вызов OSRM `/trip` при заданном финише: `source=first, destination=last`
   (старт первый, финиш последний, промежуточные точки задач — в любом порядке между ними).
   Без финиша — как сейчас: `source=first, roundtrip=false`.
4. Если задан и старт, и финиш — сетку покрытия/точки задач не деградировать: финиш не должен
   «съедать» waypoint-лимит (учесть в потолке 300 точек).

Совместимость: существующие вызовы без `end_*` работают как раньше. Обязательность старта приложение
гарантирует на клиенте — на уровне API старт остаётся опциональным.

## 3. Сервисная учётка для полевых планшетов

Приложение не хранит пароли пользователей (аутентификация — прямой SQL по `crm.users`). Для JWT-логина
в WebCRM заводится **сервисная учётка**:

1. Запись в `crm.users`: логин `field_route_service`, роль `field` (или отдельная `field_service`),
   сильный пароль. Доступ — только на эндпоинты из п. 1.
2. `POST /api/auth/login` для этой учётки должен отдавать `token` как обычным пользователям
   (роль не должна отсекаться на логине).
3. Логин/пароль сервисной учётки передаются в приложение через конфиг
   `app/src/main/assets/map_layers_config.json` (ключи `webCrmLogin` / `webCrmPassword`).
4. TTL токена `AUTH_TOKEN_TTL_HOURS` (прод 12 ч) устраивает: приложение кэширует JWT ~11 ч
   и при 401 молча перелогинивается.

Альтернатива (если не хочется держать пароль в конфиге): статический долгоживущий токен
(конфиг `ORDER_ROUTE_SERVICE_TOKEN`), который FastAPI-депенденси принимает как `Authorization: Bearer`
наравне с JWT. Что проще поддерживать — на стороне бэкенда.

## 4. nginx: таймаут build-route до 120 с

На больших полигонах построение занимает до ~2 минут (много вызовов OSRM nearest). Если сейчас
прокси рвёт POST ~60 с — поднять для локейшна `/api/crm/tasks-area/*/build-route`
(`proxy_read_timeout 120s; proxy_send_timeout 120s;`). WebCRM-фронт уже ставит 120 с на свой fetch.
GET-эндпоинты не трогаем.

## 5. Что НЕ меняется

- OSRM-прокси `http://172.21.198.219/osrm` — без изменений (в этой схеме приложение его не использует).
- Сам алгоритм движка (сетка 180 м, буфер 100 м, дедуп ≤ 300, чанки по 90, ≤ 3 итераций дожима) — без изменений.
- Таблица `crm.order_routes` — без изменений (upsert один маршрут на заказ остаётся).
- Фактические GPS-треки полевиков (`mggt_field.tracks`) — другой контур, не трогаем.

## 6. Приёмка (curl из LAN)

```bash
BASE=http://172.21.198.219
KEY=<uuid crm.tasks_area.key>

# 1) сервисная учётка логинится
TOKEN=$(curl -sS -X POST "$BASE/api/auth/login" \
  -H 'Content-Type: application/json' \
  -d '{"login":"field_route_service","password":"..."}' \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["token"])')

# 2) field-роль читает сохранённый маршрут (до этого — 403)
curl -sS -H "Authorization: Bearer $TOKEN" "$BASE/api/crm/tasks-area/$KEY/route" -o /dev/null -w '%{http_code}\n'
# ожидание: 200 (если построен) или 404 «Маршрут ещё не построен» — но НЕ 403

# 3) построение со стартом и опциональным финишем, до 120 с
curl -sS -m 120 -X POST "$BASE/api/crm/tasks-area/$KEY/build-route" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"start_lng":37.4177,"start_lat":55.8745,"end_lng":37.4301,"end_lat":55.8702}' \
  | python3 -m json.tool | grep -E 'polygon_coverage_pct|total_distance_m'

# 4) маршрут начинается у стартовой точки и заканчивается у финишной
#    (проверить route_geometry.coordinates[0] ~ start, [-1] ~ end)

# 5) обычная роль field (не сервисная) тоже проходит п. 2 — если выбран вариант без районной проверки
```

Чек-лист готовности бэка:

- [ ] роль `field`/`field_service` проходит на 4 эндпоинта (нет 403)
- [ ] `end_lng`/`end_lat` принимаются; без них — прежнее поведение
- [ ] при заданном финише маршрут заканчивается в нём (`destination=last`)
- [ ] сервисная учётка заведена, логин отдаёт токен
- [ ] nginx не рвёт POST build-route на 60 с
- [ ] регресс: построение менеджером из WebCRM работает как раньше
